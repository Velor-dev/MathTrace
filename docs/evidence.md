# Formal and computational evidence

The root registers and reviews exact source before invoking any execution operation. Worker results are proposals and never automatically run commands. All paths below are local control operations, not instructions for tool-free subagents to execute.

`ingest` accepts typed `experiment` and `formal_plan` proposals with complete `source_code`. It preserves the exact code as an artifact and binds authorship to the worker conversation. This only registers a plan: source/scope reviews, actual execution, receipt review and mathematical promotion remain separate operations.

## Computational observations

Register an `experiment` with target claim, source artifact, exact scope, inputs and author. Obtain independent `execution-scope` and `source-integrity` review, then call `run_experiment`. The receipt preserves interpreter identity, exact input hash, stdout/stderr, exit code and timeout status. A successful execution does not create mathematical support. Exhaustiveness, arithmetic validity and any reduction to the full target must be argued and independently reviewed as mathematics.

Python runs natively by default. Only for explicit `bubblewrap` execution, run `python tools/setup_execution.py` to provision the pinned Ubuntu package locally against its APT digest without root installation. A system-installed Bubblewrap is also supported on Linux. An unavailable explicitly selected sandbox fails closed without a native fallback. The following isolation details apply only to this optional backend.

The job receives source and `inputs.json` read-only under `/inputs`, with a convenience link at `/work/inputs.json`. It has read-only `/usr` excluding `/usr/local`, fresh PID/network/IPC/mount namespaces, a cleared environment, no Windows mounts, home directory, host sockets or campaign files, and ephemeral `/work`, `/tmp`, and `/outputs`. User namespace creation is disabled inside the job.

Network and host-communication isolation is enforced at two layers:
1. Bubblewrap unshares the network namespace (`--unshare-net`), isolating TCP/UDP and standard networking stacks (`AF_INET`, `AF_INET6`, `AF_PACKET`, `AF_NETLINK`), causing network connections to fail with `ENETUNREACH`.
2. Because virtualization environments (including WSL2) may leave Hyper-V socket communication (`AF_VSOCK`) reachable across network namespaces, the runner installs an argument-aware libseccomp BPF filter that explicitly intercepts and denies `socket(domain=AF_VSOCK, ...)` with `EPERM`. Furthermore, to prevent untrusted jobs from establishing asynchronous execution channels or bypassing syscall-level socket filters (e.g. via `IORING_OP_SOCKET`), the filter denies `io_uring_setup`, `io_uring_enter`, and `io_uring_register` with `EPERM`. The isolation filter fails closed: if the runner cannot resolve any required syscall or cannot prove it has installed the denial rules, execution aborts immediately. The filter also denies inherited kernel-keyring access (`keyctl`, `add_key`, `request_key`). Host Unix sockets are blocked by mount isolation.

Each writable mount (`/work`, `/tmp`, `/outputs`) is a tmpfs bounded to 128 MiB. Total captured output is limited to 4 MiB combined. The optional Bubblewrap runner applies POSIX resource limits (`RLIMIT_AS` 2 GiB, `RLIMIT_FSIZE` 128 MiB, `RLIMIT_NOFILE` 128, `RLIMIT_NPROC` 64, `RLIMIT_CPU` timeout+1s, `RLIMIT_CORE` 0). Upon wall-clock timeout or output limit exhaustion, `os.killpg` terminates the entire process group with `SIGKILL`.

Linux accounts `RLIMIT_NPROC` per real UID across all extant processes and threads owned by that UID on the system, rather than per process subtree or container slice. Under bubblewrap's user namespace, the kernel evaluates `RLIMIT_NPROC` against the caller's real UID in the initial user namespace. Thus `RLIMIT_NPROC=64` bounds the caller's total UID concurrency rather than allocating a dedicated sandbox-local process quota.

Aggregate cgroup v2 accounting is not used because unprivileged/rootless execution under WSL2 or standard user accounts cannot manage cgroup controllers without root privileges or fragile external systemd delegation. The residual availability risk is precisely bounded: because address space (`RLIMIT_AS`) is enforced per-process rather than tree-wide, multiple concurrent child processes could collectively consume virtual memory beyond a single process limit, or consume CPU cores until wall-clock expiry and process-group SIGKILL terminate the group. The boundary guarantees state integrity and filesystem/network/keyring/vsock isolation, but trusts the Linux kernel, bubblewrap, and the installed runtime. Kernel exploits and hypervisor escape vulnerabilities are outside this boundary. [Bubblewrap security model](https://github.com/containers/bubblewrap/blob/main/README.md#sandbox-security).

Source and mathematical scope review remain required. Isolation protects state and exposure boundaries; it does not make a calculation exhaustive or correct. Tool-free mathematical workers still request computation through root mediation.

## Lean plans and receipts

1. Register `formal_plan` with the original claim, exact Lean source artifact, declaration alias, expected formal type, permitted assumptions, author, proof/disproof outcome, and any ordered `library_paths`. Library manifests and the exact trusted verifier source/hash are captured before source review. The implemented profile is `lean-4.30.0-reserved-primitives-v1`, for Lean v4.30.0. A generated public root declaration preserves the exact receipt alias in module-mode source.
2. Independently review `formal-source-integrity`, `formal-target-fidelity`, and `foundations`. The packet contains the actual generated source, including the explicit type bridge and axiom query.
3. Use `install_lean` with an exact release tag. Provisioning accepts only a matching official publisher ZIP asset with its SHA-256 digest. It extracts into a fresh empty stage, verifies the exact archive file set and bytes, then atomically publishes a unique installation tree. Existing trees are never merged into the new one. It records the complete distribution, including standard libraries. Later verification rejects added files as well as missing/modified files. Arbitrary executable paths are not accepted by `run_lean`.
4. Invoke `run_lean` with the formal plan and installed toolchain ID. It commits durable execution intent first; see [execution recovery](execution.md). When explicitly selected, Lean execution is isolated via the Bubblewrap backend (`check_lean`): execution cannot add, reorder or alter the reviewed library roots; the toolchain and extra library roots are staged and mounted read-only (`/toolchain`, `/libraries/<n>`), the source is mounted read-only at `/inputs/Main.lean`, hidden Lean/library override environment variables are cleared, and Lean compiles under `/inputs` and atomically publishes `/outputs/Main.olean` on bounded tmpfs. A trusted bootstrap transfers the output-directory handle to the external recorder, then closes its export socket before running Lean. The recorder collects only bounded regular output after namespace termination, without following symlinks. The compiler explicitly uses `-j2` and an 8 GiB virtual-address-space ceiling; Python retains its 2 GiB ceiling. The earlier environment variable alone did not constrain the compiler's hardware-concurrency default.
5. The external recorder retains the complete fixed `Main.olean`, `Main.olean.server`, `Main.olean.private`, and `Main.ir` family with explicit presence/absence, sizes and actual hashes. Each part is bounded to 16 MiB and the family to 64 MiB. A separate trusted verifier loads the pristine official primitive profile before adding candidate roots, reconstructs the selected theorem over that profile, checks exact declaration correspondence, and writes a complete checked-target report to its own retained output file. Inspect-only exports do not qualify. Compiler stdout is diagnostic; the structural checked axiom closure is authoritative.
6. A modern receipt binds the exact plan, source, helper, toolchain, execution request, terminated compilation outputs, checked semantic capsule, primitive reference and reconstructed module resolution. The resolution is checked against actual staged byte manifests; it is reconstructed under immutable roots, not an open-file trace. The canonical validator reconstructs those bindings from the immutable terminal observation, including which exact receipt the terminal event names. The frozen candidate includes all these artifacts and the terminal observation.
7. Independent packets supply bounded exact mathematical views of the compiled root type, all material definition/opaque bodies, inductive/constructor/recursor semantics and actual foundation schemas. Referenced theorem proof bodies remain in the capsule and are omitted only from the statement-meaning view. Binary/helper/reference/resolution records expose identities and expansion locators; arbitrary process text and earlier review identities are omitted. Extra libraries remain operator-selected local trees without verified publisher identity. Canonical state retains the full evidence, except imported library/toolchain bytes, whose exact manifests remain recorded.
8. Independently review the resulting receipt for `formal-receipt`, `formal-target-fidelity`, and `foundations` before it becomes eligible for a formal inference. Final candidate audit additionally checks the formal environment and original-target mapping.

The supported foundational declarations are `propext`, `Classical.choice`, and `Quot.sound`, with exact schemas compared against the reference profile. A plan cannot expand its contract's policy. A constructive contract can choose a smaller foundation. Custom axiom-name policies are explicitly unsupported until a justified profile supplies their exact schemas. An assumption ID alone does not establish that the compiled theorem faithfully represents that assumption as an antecedent.

Checking uses the same pinned Lean kernel; no independent-checker assurance can be selected. Source-to-object correspondence remains explicitly unverified. The observed association is that the exact reviewed source was supplied and the terminated compilation's outputs were collected. Neither process success nor exact staged bytes establish original-target fidelity. [Lean proof-validation guidance](https://lean-lang.org/doc/reference/latest/ValidatingProofs/).

## Exact review expansion

A passing `formal-target-fidelity` review requires complete compiled statement coverage and the exact original claim, contract, definitions, assumptions and outcome. `foundations` and `formal-receipt` require complete foundation coverage and the pinned policy/profile/helper identities. `formal-environment` requires both views and assesses this selected theorem's checking context under the pinned profile, with the stated provenance/correspondence limitations. These gates prove exposure, not the correctness of the reviewer's judgment.

When the default 32,000-character semantic view is incomplete, request exact declaration selectors from that capsule. `expand_semantics` accepts `task`, `capsule`, `selectors`, root `reason`, and optional `max_chars` (default 128,000, allowed 1,000–8,388,608). It creates a new immutable packet, preserving blindness only for a capsule already admitted through that exact target's receipt closure. The complete previously supplied/requested union must fit the budget. Root rationale stays in history; the blind packet contains a fixed mechanical description. The old review never gains retroactive coverage. New receipts, arbitrary artifacts and other reviewers' verdicts require the normal informed-admission path. For a pending native context request use `resolve_semantic_context` with its exact result ID and the same expansion arguments.

For a concrete proof-dependency concern, `include_theorem_proofs: true` supplies the exact selected theorem bodies within the same bound capsule and budget. Their referenced dependencies may need further selectors; the view explicitly says so. Later expansions retain that proof exposure. Reading every unrelated reference declaration or theorem proof is not a default fidelity requirement.

## Invalidation and historical evidence

The [checked compiled-evidence contract](../openspec/specs/formal-and-computational-evidence/spec.md) is integrated into current formal eligibility. Legacy history remains readable, but old checked flags do not qualify under this profile. Migration requires a new modern plan/check, fresh compiled fidelity assessment, a new inference/counterexample binding, and a new freeze/audit. Recovery of an already-started legacy attempt retains its original writer/assurance; deploying the new writer never upgrades it.

Withdrawing a formal source, plan, receipt, compiled artifact, permitted scope or toolchain invalidates its current use without rewriting the historical execution. An independent alternate proof can remain eligible. If the compiled `.olean` artifact is withdrawn or modified, `_formal_current` evaluates to `False` and any dependent machine-checked candidate is invalidated immediately.

Historical currentness checks exact stored plan/toolchain/target/outcome/replay bindings and provenance. It does not rehash today's installed files on every query: a changed or removed present installation does not retroactively change which exact staged environment performed a historical proof check. New execution verifies bytes before staging and after checking. A finding against the recorded checker/toolchain still suspends dependent historical receipts.

The test suite exercises actual isolated Python execution, interruption recovery and deterministic formal gates. Prior real Lean proof/sorry/invalid and fresh replay evidence remains retained. The modern isolated module-proof channel also passes, with the complete primitive reference and actual staged resolution binding in `work/validation/formal/validation-module-proof-profile.json`. Targeted synthetic protocol tests cover diagnostic spoofing, incomplete/inspection-only reports, exact byte/request/terminal identity, missing context, bounded blind expansion and withdrawal. They do not establish real reviewer independence or mathematical fidelity judgment. R3-H2 now records actual qualified source review, isolated execution/recovery and a new exact native receipt review. The final project audit is complete at these accepted scopes; see [native scope/limits](native-capture.md).

## Native checking and historical evidence

Direct Execution is the default on Windows, Linux and macOS, using the same source/foundation reviews, pinned v4.30.0 primitive profile, full compiled-file family, semantic inspection and independent receipt/candidate gates. Choose the optional `execution_mode` argument consistently for `install_lean`, `run_lean` and `run_experiment`; `bubblewrap` remains explicit and has no native fallback. Native target assets are Windows x86-64, Linux x86-64/AArch64 and macOS x86-64/AArch64. Publisher digests and complete manifests remain mandatory; executable names and Unix permissions are platform-specific.

Native execution stages byte-verified copies and records platform-native physical roots with stable toolchain/library/replay roles. Exact ordered roots and resolved parts are checked against the committed manifests. The helper's explicit output destination avoids privileged guest paths. Pristine reference imports exclude candidate roots and ambient overrides. These are trusted-local-host observations, not enforced input immutability against hostile same-user code. See [execution](execution.md) for process cleanup and resource-limit differences.

Process success, mathematical checking, environment metadata and sandbox attestation are distinct. Successful native computations are observations with isolation false; failed calculations are not refutations. Modern native proofs require the same semantic/axiom/fidelity evidence as sandbox checks. v2 receipt manifests bind the mode-aware request and recorded environment. v1 sandbox receipts retain all original namespace and guest-root validation, and pre-profile legacy evidence remains ineligible. History is never rewritten to upgrade assurance or adopt a new default.

The modern helper performs pristine primitive-context replay and exact declaration comparison; `leanchecker --fresh` is retained for the separate standalone validation path. Neither is an independent kernel. Full source-to-object correspondence remains unverified. Candidate freezing, evidence withdrawal, independent fidelity/foundation review, nonparty objection disposition and release eligibility are unchanged. Execution mode cannot repair missing Codex transcript qualification or replace independent audits.
